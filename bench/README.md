# 성능 측정 (bench)

"측정하지 않은 최적화는 추측"이라서, 저장 방식을 바꿀 때마다 숫자로 비교한다.

## 시세 저장 방식 비교

```bash
node bench/tick-storage.mjs
```

- Docker로 postgres/redis가 켜져 있어야 한다. 스크립트가 모드마다 백엔드를 **재시작**하므로 약 4분 걸린다.
- 비교 대상
  - `direct` : 시세 1건마다 바로 INSERT (나쁜 예)
  - `batch`  : 메모리 버퍼에 모았다가 1초마다 다중 행 INSERT (기본값)
- 끝나면 `bench/results-tick-storage.md`에 표가 저장되고, 서버는 기본 모드(`batch`)로 돌아온다.

직접 모드를 바꿔서 띄우려면:
```bash
TICK_STORAGE_MODE=direct docker compose up -d backend
```
```bash
docker compose up -d backend
```
(두 번째는 환경변수 없이 실행하는 것이라 기본값 `batch`로 돌아온다.)

## 측정 결과 (초당 약 1,000건 발행, 30초)

| 지표 | direct (틱마다 INSERT) | batch (버퍼 + 1초 배치) |
|---|---|---|
| 초당 발행 | 1,003건 | 1,001건 |
| 초당 처리 | **636건** | **1,001건** |
| 밀린 양 | **15,960건** (계속 늘어남) | 0건 |
| 지연 평균 | **9,772ms (약 10초)** | **17ms** |
| 지연 최대 | 15,965ms | 185ms |
| CPU postgres | 13.7% | 1.5% |
| 유실 / 순서 역전 | 0 / 0 | 0 / 0 |

해석
- `direct`는 한 건마다 DB 왕복과 커밋을 치르느라 초당 약 640건밖에 못 처리한다. 들어오는 속도(1,000건)가 처리 속도보다 빨라
  밀린 양이 계속 쌓이고, 화면에 보이는 시세가 점점 과거 것이 된다 (지연 약 10초).
- `batch`는 수신 스레드가 버퍼에 넣기만 하므로 발행 속도를 그대로 따라가고(지연 17ms), DB에는 1초에 몇 번의 다중 행 INSERT만 보낸다.
  postgres CPU도 약 9배 낮다.
- 측정 중 브라우저 탭 1개가 연결되어 있었다 (두 모드 모두 같은 조건).

> 이 표는 처음 만든 스크립트의 버그를 고친 뒤의 값이다. 처음에는 측정 시간을 반복 횟수로 가정해서 실제(약 55초) 대신 30초로 나눠
> "초당" 수치가 약 1.8배 부풀려졌다(발행이 1,867건/초로 나와서 이상함을 발견). 지금은 시계로 실제 경과 시간을 잰다.

## 지표 직접 보기

서버가 떠 있으면 아래 주소에서 언제든 확인할 수 있다 (`/actuator/metrics/{이름}`).

| 이름 | 의미 |
|---|---|
| `ticklock.ticks.published` | 생성기가 발행한 건수 |
| `ticklock.ticks.received` | 구독자가 처리를 끝낸 건수 (발행과의 차이 = 밀린 양) |
| `ticklock.ticks.stored` | DB에 저장된 건수 |
| `ticklock.ticks.dropped` | 버퍼가 가득 차 버린 건수 |
| `ticklock.ticks.store_failed` | DB 저장 실패로 잃은 건수 |
| `ticklock.ticks.out_of_order` | 발행 순서와 다르게 도착한 건수 |
| `ticklock.ticks.lag` | 발행 → 처리 완료까지 걸린 시간 |
| `ticklock.ticks.queue.size` | 배치 버퍼에 쌓여 있는 건수 (batch 모드) |

## 측정하다가 알게 된 것들

- **Redis 메시지 처리 순서**: 기본 설정은 메시지마다 새 스레드를 만들어 처리해서, 약 4만 건 중 179건(0.45%)이 순서가 뒤바뀌어 도착했다.
  처리 스레드를 1개로 고정한 뒤 약 3.2만 건 기준 0건이 되었다.
- **주문 등록 지연**: 서버를 막 띄운 직후에는 평균 약 1.5초였지만, 데워진 뒤에는 평균 약 85~90ms였다.
  초기 지연은 JVM/Hibernate 콜드 스타트 때문이었다. 부하 테스트는 워밍업 이후 수치를 기준으로 봐야 한다.
